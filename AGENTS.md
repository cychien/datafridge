# Project agent memory

This file is the project's committed home for project-intrinsic agent knowledge: build, test, release, architecture, and sharp-edge notes that should travel with the code.

- The library is one invariant: **when the app wants data, it always has some** - not necessarily current, but always there and as current as upstream allows. The six-guarantee semantic contract must never be violated: a read with data never waits and never touches upstream; a read with none triggers exactly one coalesced fetch inside its `timeout`; upstream calls never exceed a source's declared rate whatever caused them; throttled work never starves and never fails for nothing; a failure keeps last-known-good, backs off, re-claims after a dead lease, and rejects late writes on version; invalid configuration throws at construction. `docs/api.md` and `docs/zh-TW/api.md` carry the shipped surface. Do not resurrect the implementation-time DESIGN.md, and never link to a gitignored working file from committed docs.
- **All upstream calls leave through `packages/core/src/dispatcher.ts`.** A scheduled tick, a read miss and an `anyParams` call are the same work through different doors: claim the lease (an ephemeral call has none), run under the deadline, write back under a version check, reschedule or back off. Quota, concurrency and backoff live there once. `test/dispatcher.test.ts` is the guard that no second path grows back - keep it passing rather than working around it.
- **One read path, `packages/core/src/read-path.ts`**, used by both `createFridge.read` and `createReader`. A reader holding a full Store gets the dispatcher and can fetch; a results-only one serves and waits. Do not let the two drift into separate implementations.
- Commands (repo root): `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm build`. All four must be green before any change is done.
- `packages/core` has zero runtime dependencies and never touches the wall clock: no `Date.now`, `Math.random`, or global timers (eslint enforces this). The single sanctioned exception is `src/system-clock.ts`, which provides the default `systemClock`/`systemRandom`; `clock` and `random` stay injectable and tests use `FakeClock` from core - no sleeps, no wall-clock dependence.
- Every Store adapter must pass `storeContractSuite` from `@datafridge/core/contract-tests` (see `packages/core/test/contract.test.ts` for usage). The suite documents semantics beyond the type signatures: create-on-claim at expectedVersion 0, quota windows that are fixed, epoch-aligned and never rewound, and `releaseQuota` (credits back only the window it was taken in, never below zero). Core never asks a store to enumerate itself: `listDue` always carries a finite limit.
- Invalid configuration fails at construction (`defineQueries`, `createFridge` resolution rules), never at runtime.
- `packages/cloudflare` typechecks and tests against core's source (tsconfig `paths` + vitest `resolve.alias`) because CI runs test before build; the tsup build uses `tsconfig.build.json` and resolves core from dist via pnpm's topological build order.
- Cloudflare tests run on vitest 4 with the `cloudflareTest()` plugin from `@cloudflare/vitest-pool-workers` (no more `defineWorkersConfig`/`poolOptions`). Sharp edges: storage isolation is per test *file* (wipe D1 tables between tests), test files and the main worker do not share a module cache (inject test state into a DO via `runInDurableObject`), and due DO alarms auto-fire in workerd (await the ignition tick by polling, drive later ticks deterministically with `runDurableObjectAlarm`). `workerd` must stay in pnpm `onlyBuiltDependencies`. The pool evaluates modules inside a request context, so it cannot see workerd's global-scope bans (no `AbortController`, timers or randomness at module top level); the `example-cloudflare-basic` vitest project boots `examples/cloudflare-basic` under a real `wrangler dev` because that is the only witness.
- The installed `datafridge init` CLI lives in `@datafridge/cloudflare` as a node bin, per the packaging rules in `docs/writing-adapters.md#packaging-rules`: no extra package, no sibling deps. `smol-toml` stays a devDependency bundled into `dist/cli.js` via tsup `noExternal` so the package keeps zero runtime deps. Node-typed CLI code is fenced off from workers-typed code: `src/cli` is excluded from the workers tsconfigs and owned by `tsconfig.cli.json`, and its tests run in the separate `cloudflare-cli` vitest project (`test-cli/`, plain node) because the main cloudflare project forces the workers pool.
- Parameterized queries are specified in `docs/api.md#parameterized-queries`. `queryKey` hashes canonical JSON into the reserved `@df/v1/` identity; params are snapshotted, must stay finite/non-secret, and each variant is an ordinary independent registry entry. Keep identity, reconcile, direct-read, and DO+D1 lifecycle coverage deterministic.
- **Being an entry is what the registry decides, never what somebody asked for.** An `anyParams` base has no list and no entries: params the registry does not name are answered by one ephemeral dispatcher call and nothing is stored - no result, no row, no membership. `docs/api.md#open-parameter-spaces`.
- **D1 is the whole coordination plane on Cloudflare.** `FridgeDO` keeps no schedule, lease, quota or dispatch state in its own SQLite - only the registry signature it last ignited for - so a Durable Object, a cron trigger and any number of request-path readers coordinate through the store. Reads never route through the singleton object; the request path is `createReader` over the same `d1(env.DB)`.
- **A tick bounds itself; there is no knob.** One bounded page of rows, a bounded number of departed-row deletions, admission only while a call's own `timeout` fits the driver's `budgetMs`, and no second ask of a source that already refused this tick. `runDue` returns `nextRunAt` so a driver re-arms without re-reading storage. Page sizes stay private to `engine.ts`. The page bounds *scanning*, never *knowing*: a registry name the page did not reach is read by name (`fillMissingRows`), because inferring "no row" from a full page either re-claims rows that exist or never starts ones that do not.
- **Concurrency and coalescing are store state, not process state.** `maxConcurrent` is a permit row per in-flight call (expiring, so a dead holder recovers), and overlapping reads of params the registry does not name join a generation-scoped *flight* so the cohort costs one call and one quota slot. Both live in `SchedulePlane` precisely so two Workers are one ceiling and one call, not two of each; the in-process semaphore survives only as prompt same-instance hand-off in front of the permit.
- Release readiness is checked by `pnpm release:check`; `.github/workflows/release.yml` only publishes from a captain-dispatched run on `main` through the protected `npm` environment, authenticating with npm Trusted Publishing (OIDC) - there is no npm token and no Actions secret, so never reintroduce `NODE_AUTH_TOKEN` or `registry-url`. Unscoped names are not placeholder packages, and `1.0.0` is published locally by the captain; see `docs/releasing.md`. `changesets/action` must stay on the `v1` line: `v2` requires `@changesets/cli` v3 and hard-fails against the v2 CLI this repo installs, and the `select-mode`/`version`/`publish` subpath actions exist only in `v2`, so the action and the CLI move together or not at all.
- The publish chain is `changeset publish` -> `pnpm publish` -> `npm publish <tarball>`, and each hop matters: pnpm is what rewrites `workspace:` ranges, npm is what authenticates and generates provenance, and pnpm resolves that npm next to the running node binary rather than from `PATH`. `pnpm --filter <pkg> publish` takes a different pnpm path that drops forwarded flags, so per-package publishing must `cd` into the package.
